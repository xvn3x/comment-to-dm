# Comment to DM — контекст и правила работы для Claude

Прочитай этот файл целиком **до любых правок**, затем изучи текущий diff, `README.md`, `SECURITY.md` и непосредственно затрагиваемые файлы. Этот файл — постоянная инструкция проекта. Если пользователь просит новую задачу, сначала кратко перескажи, какие ограничения из этого документа относятся к ней, и только потом предложи план.

## 1. Что это за продукт

Comment to DM — self-hosted приложение для автоматизаций одного Instagram Professional Account. Владелец разворачивает собственную копию, создаёт собственное приложение Meta, подключает Instagram официальным OAuth и хранит все секреты и данные на своём сервере.

Главная ценность продукта: простой, понятный и надёжный аналог небольшой части ManyChat без ежемесячной подписки и без многопользовательского SaaS.

Текущая версия: `0.8.0`.

## Запросы на установку

Если пользователь просит установить или развернуть проект, сначала полностью прочитай `docs/AI-INSTALL.md` и следуй этому протоколу. Считай пользователя нетехническим, веди его по одному шагу, не запрашивай пароли/токены в чат и не автоматизируй Meta consent. Общие правила для coding agents также находятся в `AGENTS.md`.

Основной рабочий сценарий:

1. Пользователь оставляет комментарий с ключевым словом.
2. Приложение при необходимости публично отвечает на комментарий.
3. Приложение при необходимости отправляет private reply в Direct.
4. Сообщение может содержать postback-кнопку для добровольной проверки подписки или HTTPS-кнопку материала.
5. При включённой проверке подписки материал выдаётся только после разрешённой Meta проверки.

Также уже существуют простые триггеры входящих Direct и ответов/реакций на Stories. Это не полноценный inbox и не конструктор сложных цепочек.

## 2. Неподвижные продуктовые границы

- Одна установка обслуживает один Instagram-аккаунт.
- Это не многопользовательский SaaS.
- Используется только официальный Meta/Instagram API.
- Никогда не добавлять scraping, cookies Instagram, хранение пароля Instagram, эмуляцию приложения или обход review/лимитов Meta.
- Пароль Instagram вводится только на странице Meta/Instagram и никогда не попадает в это приложение.
- Не добавлять внешнюю телеметрию, рекламные пиксели или стороннюю аналитику без прямого согласования с пользователем.
- Не выдавать оценочные данные за реальные. Все показатели панели должны приходить из БД/API.
- Inbox сознательно не входит в текущий интерфейс. Журнал показывает технические события без текста входящих сообщений.
- Открытие ссылки уже отслеживается локально через `/r/:token`. Это означает HTTP-открытие URL и не гарантирует, что переход совершил именно человек: возможен prefetch/link scanner.

## 3. Что уже реализовано

- Правила для комментариев, входящих Direct и ответов/реакций на Stories.
- Все публикации или выбранный Post/Reel.
- `contains`, `exact` и `any` matching.
- Несколько ключевых слов.
- До десяти вариантов публичного ответа.
- Публичный ответ и Direct включаются независимо.
- Сообщение в Direct с кнопкой материала.
- Опциональная проверка подписки после добровольного postback.
- Повторная postback-кнопка, если подписка ещё не найдена.
- Follow-up с задержкой и автоматической отменой после открытия ссылки.
- Долговечная PostgreSQL-очередь, idempotency, retries, jitter, circuit breaker, watchdog и leader lease.
- Адаптивное замедление по заголовкам использования Meta.
- Surge mode и приоритет Direct при большой очереди.
- Панель очереди, health state, аналитика за 24 часа, воронка правил и журнал событий.
- Светлая и тёмная темы и переключение RU/EN прямо из шапки; отдельного экрана настроек нет.
- Русский и английский интерфейс.
- Десктопная и мобильная версии.
- Mock-режим, burst test и интеграционные проверки.
- Шифрование App Secret и access token.

## 4. Техническая архитектура

- Client: React 19 + TypeScript + Vite.
- Server: Fastify + TypeScript.
- Database: PostgreSQL через пакет `postgres`.
- Worker: встроенный процесс очереди; leader lease не допускает параллельную отправку одного аккаунта несколькими репликами.
- Production: Docker Compose + Caddy + PostgreSQL на отдельном VPS.
- Railway остаётся только поддерживаемой альтернативой для самостоятельного развёртывания; текущая production-установка на Railway удалена.

Ключевые файлы:

- `src/client/App.tsx` — все текущие экраны и UI-логика.
- `src/client/styles.css` — дизайн, темы и responsive breakpoints.
- `src/client/i18n.ts` — RU/EN строки.
- `src/client/types.ts` — клиентские DTO и формы.
- `src/server/app.ts` — Fastify routes, OAuth, API и webhooks.
- `src/server/automation.ts` — разбор Instagram событий и постановка задач.
- `src/server/worker.ts` — обработка очереди и восстановление.
- `src/server/meta.ts` — официальный Graph API и классификация transport/ambiguous ошибок.
- `src/server/rate-control.ts` — retries, backoff, rate limit и health decisions.
- `src/server/db.ts` — схема и миграции.
- `src/server/security.ts` — сессии, шифрование и подписи Meta.
- `tests/` — unit/regression tests.
- `scripts/` — integration, migration и burst tests.

Не переносить проект на другую платформу и не заменять текущую архитектуру без прямого запроса пользователя.

## 5. Дизайн: источник истины

Текущий интерфейс в `App.tsx` + `styles.css` уже является утверждённой основой. Он был собран по макету Claude, затем исправлен по замечаниям пользователя. Старый экспорт макета может быть полезен как справка, но **не имеет приоритета над текущим рабочим интерфейсом и этим файлом**.

Обязательные свойства интерфейса:

- профессиональный минималистичный вид;
- спокойная тёплая палитра основного интерфейса;
- одинаковая информационная архитектура в обеих темах;
- полная RU/EN локализация;
- корректная работа от ширины 320 px;
- большие понятные области нажатия;
- читабельные подписи, нормальный вертикальный ритм и отсутствие «стены текста»;
- ничего не должно наезжать друг на друга или вызывать горизонтальный скролл;
- длинные имена, сообщения, ссылки и ключевые слова должны переноситься или обрезаться безопасно;
- длинные списки и Direct-переписка должны прокручиваться внутри предназначенной области;
- fixed mobile navigation не должна закрывать последний контент;
- формы должны сохранять фокус при вводе и во время фонового обновления данных.

### Что нельзя менять без предварительного согласования

- состав и порядок основных разделов (сейчас их три: автоматизации, журнал, подключение);
- общую композицию dashboard;
- способ добавления ключевых слов как chips;
- способ добавления вариантов ответа отдельными строками;
- структуру редактора правил;
- внешний вид и смысл Direct preview;
- типографику, палитру, размеры ключевых блоков и навигацию, если это не исправление явного дефекта;
- реальные показатели или их смысл;
- удаление работающей функции ради упрощения дизайна.

Если видишь спорное дизайнерское решение, сначала опиши проблему пользователю и предложи 1–2 точечных варианта. Не выполняй самостоятельный redesign.

## 6. Instagram Direct preview

Предпросмотр нужен, чтобы пользователь максимально близко увидел, как автоматизация будет выглядеть в Instagram Direct. Это **не макет телефона**.

Обязательно:

- показывать только интерфейс Direct;
- не рисовать время устройства, мобильный сигнал, Wi-Fi, батарею, рамку телефона или home indicator;
- не пытаться подделывать реальное фото профиля;
- использовать однотонный тёмный круг с автоматически вычисленными инициалами аккаунта;
- оставить Instagram-похожую чёрную область чата, верхнюю строку, системный текст про комментарий, входящие карточки, встроенные postback/URL-кнопки, фиолетовое исходящее сообщение после postback и строку ввода;
- иконки звонка/видео/другие действия справа сверху не нужны;
- все пользовательские тексты в preview должны обновляться из формы сразу;
- длинный текст должен переноситься внутри пузыря;
- Direct thread должен иметь внутренний scroll при переполнении;
- если Direct отключён, показывать понятное состояние «только публичный ответ», а не фиктивную переписку.

Не заменяй embedded postback на отдельный quick-reply chip: в текущем сценарии кнопка находится внутри сообщения, а после нажатия Instagram показывает отправленную пользователем фиолетовую реплику.

## 7. Важные React-регрессии

Ранее редактор терял фокус после каждой клавиши и Space прокручивал страницу. Причина была в нестабильной identity вложенных компонентов при рендере.

Сейчас вложенные экранные функции внутри `App` вызываются как render helpers (`RuleEditor()`, а не `<RuleEditor />`), поэтому их DOM не размонтируется при каждом `setState`. У этих helper-функций нельзя добавлять hooks. Если нужна полноценная компонентная архитектура, вынеси компоненты на module level и передай props/context; после этого отдельно проверь focus retention.

Нельзя:

- превращать текущие render helpers в JSX-компоненты внутри `App`;
- перезаписывать редактируемую форму результатом 5-секундного polling;
- менять `key` поля на значение, которое меняется при вводе;
- перехватывать Tab в chip input;
- превращать Enter внутри textarea в неожиданный submit.

Обязательная regression-проверка после правок редактора:

1. Ввести в название `текст с пробелами` посимвольно.
2. Убедиться, что input остаётся `document.activeElement`.
3. Подождать больше 5 секунд и продолжить ввод.
4. Убедиться, что `scrollY` не изменился из-за Space.
5. Повторить для поиска в журнале и полей подключения.

## 8. Данные и backend-инварианты

- Все webhook события сначала надёжно сохраняются в PostgreSQL; только затем webhook подтверждается.
- Уникальные Instagram IDs и idempotency keys защищают от дублей.
- Public reply с неопределённым результатом нельзя слепо повторять: сначала сверка.
- Private reply повторяется только по существующим правилам safe/ambiguous recovery.
- Auth/permission/restricted состояния не должны расходовать очередь.
- Секреты всегда шифруются `SecretBox`; не логировать их и не отдавать клиенту.
- Подпись webhook и signed callbacks Meta всегда проверяется.
- Не хранить текст входящих комментариев и Direct в журнале.
- Миграции БД должны быть additive и безопасными для уже работающей Railway БД.
- Нельзя удалять столбцы/таблицы или менять смысл существующих статусов без отдельного migration plan.
- Не увеличивать число worker-реплик для ускорения одного аккаунта: лимит Meta общий.
- Не заявлять конкретный безопасный лимит сообщений, если Meta его официально не гарантирует.

## 9. Локализация и доступность

- Любая новая видимая строка должна иметь RU и EN варианты.
- Не оставлять hardcoded English aria-label в русском интерфейсе.
- Активные navigation/segmented controls должны иметь корректные ARIA состояния.
- Ошибки и статусы должны иметь `role="alert"`/`aria-live` там, где это уместно.
- Контраст текста и controls проверять в обеих темах.
- Не уменьшать служебный текст ниже читаемого размера ради соответствия макету.
- Управление chips, variants, toggles и navigation должно работать клавиатурой.

## 10. Процесс изменения

Перед правкой:

1. `git status --short` — не перезаписывать чужие незакоммиченные изменения.
2. Прочитать текущую реализацию и связанные тесты.
3. Выполнить baseline: `npm test`, `npm run build`, `npm run lint`.
4. Кратко перечислить затрагиваемые инварианты.

Во время работы:

- делать минимальные целевые изменения;
- не переписывать весь `App.tsx`/`styles.css` ради локальной задачи;
- использовать существующие tokens/components;
- не добавлять зависимость, если текущий stack решает задачу;
- не менять backend вместе с дизайном без функциональной необходимости;
- не публиковать секреты в diff, логи, скриншоты или документацию.

После работы:

```bash
npm test
npm run build
npm run lint
```

Для изменений схемы/очереди также, и только на отдельной одноразовой базе:

```bash
ALLOW_DESTRUCTIVE_TEST_DB=1 INTEGRATION_DATABASE_URL=postgres://USER@127.0.0.1:5432/comment_to_dm_test npm run test:migration
ALLOW_DESTRUCTIVE_TEST_DB=1 INTEGRATION_DATABASE_URL=postgres://USER@127.0.0.1:5432/comment_to_dm_integration npm run test:integration
```

`test:integration` очищает таблицы, `test:migration` выполняет `DROP SCHEMA public CASCADE`. Guard в `scripts/test-db-guard.mjs` не даст запустить их без `ALLOW_DESTRUCTIVE_TEST_DB=1`, без `INTEGRATION_DATABASE_URL`, на базе без `test`/`integration` в имени и на базе, совпадающей с `DATABASE_URL`. Лиза worker сбрасывается самим тестом внутри одноразовой базы — рабочую базу для этого править нельзя.

Новые индексы добавлять и в `baseSchema`, и отдельной additive-миграцией: на свежей установке миграции только помечаются применёнными, их SQL не выполняется.

Burst test запускать только в mock/local окружении, никогда против live Meta:

```bash
npm run test:burst -- http://127.0.0.1:3000 5000 25
```

## 11. Обязательная visual QA matrix

Проверить dashboard, журнал, подключение, создание/редактирование правила и login:

| Width | Тип |
| ---: | --- |
| 320 | маленький телефон |
| 375 | обычный телефон |
| 768 | планшет |
| 1024 | небольшой desktop/tablet landscape |
| 1440 | desktop |
| 1920 | широкий desktop |

Для каждого ключевого экрана:

- `document.documentElement.scrollWidth <= window.innerWidth`;
- нет перекрытий текста, кнопок и карточек;
- bottom nav не скрывает финальный контент;
- sticky/fixed элементы не закрывают поля формы;
- все кнопки доступны и подписи не обрезаны бессмысленно;
- длинный RU и EN текст не ломает сетку;
- светлая и тёмная темы не теряют контраст;
- внутренний scroll Direct preview и длинных списков работает;
- на 320/375 px форма ввода не вызывает масштабирование/горизонтальный сдвиг.

Не ограничивайся скриншотом полной страницы: fixed/sticky элементы на full-page screenshot могут выглядеть в неверном месте. Проверь обычный viewport и прокрутку живой страницы.

## 12. Deployment

Production размещён на отдельном HOSTKEY VPS. Его адрес, SSH-реквизиты и runtime secrets не должны появляться в публичном репозитории, issue, логах или документации.

Перед push:

- убедиться, что все проверки зелёные;
- показать пользователю краткий список изменений;
- не менять production `.env` и серверные secrets без необходимости;
- не добавлять `.env` в Git.

Push в `main` запускает CI и отдельный production deploy на сервер сопровождающего проекта. Перед обновлением сервер создаёт backup; после обновления нужно проверить `/health`, `/ready`, login, dashboard и затронутый сценарий. Не считать локальную сборку доказательством корректного production deploy. Pull request и push в чужой fork не получают deploy secrets и не обновляют production.
