# Comment to DM

[![CI](https://github.com/xvn3x/comment-to-dm/actions/workflows/ci.yml/badge.svg)](https://github.com/xvn3x/comment-to-dm/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-2f312d.svg)](./LICENSE)

Self-hosted приложение для одного Instagram Professional Account: комментарии, входящие Direct и ответы на Stories запускают настраиваемые сообщения с кнопками, проверкой подписки и follow-up.

Приложение работает на сервере владельца. Оно не отправляет токены, комментарии или статистику разработчику проекта и не просит пароль от Instagram. Для подключения используется собственное Meta-приложение владельца и официальный OAuth.

> Проект находится в beta-версии 0.8.1. Перед подключением важного аккаунта сначала проверьте сценарий на тестовой публикации. Использование официального API снижает риски, но не гарантирует отсутствие ограничений со стороны Meta.

## Возможности v0.8.1

- одна установка — один Instagram Professional Account;
- конкретный Post/Reel или все публикации;
- ключевые слова, точное совпадение или любой комментарий;
- автоматизация входящих Direct по ключевому слову, точному совпадению или любому сообщению;
- автоматизация прямых ответов и emoji-реакций на Stories;
- до десяти вариантов публичного ответа;
- ответ на комментарий может работать самостоятельно, без сообщения в Direct;
- необязательное private reply в Direct для правил по комментариям;
- необязательная HTTPS-кнопка;
- необязательная выдача материала только после добровольного нажатия postback-кнопки внутри сообщения и проверки подписки;
- повторная кнопка проверки, если пользователь ещё не подписан, без повторного комментария;
- необязательный follow-up в пределах разрешённого Meta окна: ссылка на материал отслеживается локально, а напоминание отменяется после её открытия;
- проверка подписки через долговечную очередь: webhook отвечает быстро, а временные ошибки Meta повторяются безопасно;
- защита от повторной отправки одному человеку для того же правила и публикации;
- долговечная приоритетная очередь с повторами при временных ошибках Meta;
- адаптивное замедление по служебным заголовкам Meta и общая пауза аккаунта при rate limit;
- безопасное восстановление после обрыва запроса без слепой повторной публичной отправки;
- автоматическая проверка токена и подписок `comments`, `messages` и `messaging_postbacks`, контролируемое обновление long-lived token;
- circuit breaker для ошибок авторизации, разрешений, ограничений аккаунта и временных сбоев;
- leader lease в PostgreSQL: при двух репликах только один worker отправляет сообщения;
- watchdog зависших заданий, семидневный дедлайн и режим всплеска с приоритетом Direct;
- контроль backlog, скорости и состояния очереди из панели администратора;
- адаптивная панель для компьютера и телефона, светлая и тёмная темы, интерфейс на русском и английском;
- реальная аналитика с выбором периода: сегодня, конкретная дата, произвольный диапазон или вся доступная история;
- график отправок с автоматическим шагом: по часам для одного дня, по дням для длинных периодов;
- подсказка по каждому столбику с разбивкой на ответы на комментарии, сообщения в Direct и напоминания;
- подробная разбивка по клику на общем числе: из чего оно складывается и что было дальше — подтверждённые и неподтверждённые проверки подписки, переходы по ссылке и переходы после напоминания;
- выбранный период применяется к воронке каждого правила и к счётчику ошибок;
- очередь, скорость и открытия материала в реальном времени;
- клики по настроенным кнопкам считаются локально, без cookies и сторонних аналитических сервисов;
- подробный журнал статусов и исходящих ответов на 30 дней без хранения текста входящих комментариев и сообщений;
- отдельные экраны подключения и готовности Meta и журнала автоматизаций;
- переключатели языка и темы вынесены в шапку, политика конфиденциальности — в нижний колонтитул;
- mock-режим для проверки без Instagram;
- зашифрованное хранение App Secret и access token.
- ежедневная резервная копия PostgreSQL и production-конфигурации с проверкой восстановления в одноразовой базе.

## Быстрое развёртывание на VPS

### С помощью Codex или Claude Code — рекомендуется для первого пользователя

Отправьте AI-агенту ссылку на репозиторий и напишите:

> Помоги установить этот проект на мой VPS. Сначала прочитай `AGENTS.md` и `docs/AI-INSTALL.md`. Я раньше не настраивал серверы: веди меня по одному шагу, ничего не удаляй без подтверждения и не проси присылать пароли или токены в чат.

Агент проверит сервер, выполнит безопасную часть установки и будет в реальном времени говорить, куда нажимать в Meta. Вход в Meta/Instagram, принятие приглашения тестировщика и выдачу разрешений подтверждает сам владелец аккаунта.

### Самостоятельно

Потребуется зарубежный VPS с Ubuntu 24.04, публичный IP, 2 ГБ RAM и открытые TCP-порты 80/443. Платный домен не нужен: установщик создаст бесплатный HTTPS-адрес через `sslip.io`.

```bash
apt update && apt install -y git
git clone --depth 1 --branch v0.8.1 https://github.com/xvn3x/comment-to-dm.git /tmp/comment-to-dm
cd /tmp/comment-to-dm
sudo bash scripts/install-vps.sh ВАШ_IP
```

Установщик покажет пароль администратора один раз, запустит PostgreSQL/Caddy и включит ежедневный backup. Сохраните пароль в менеджере паролей.

Полная пошаговая инструкция для человека без опыта разработки: **[docs/INSTALL-RU.md](./docs/INSTALL-RU.md)**.

## Безопасность

Установщик генерирует уникальные случайные ключи отдельно для каждой установки; случайный admin password здесь безопаснее придуманного короткого пароля. Секреты остаются в `.env` на VPS с правами `0600`, а App Secret и Instagram token дополнительно шифруются в PostgreSQL. Репозиторий, контейнеры, сессии, webhook-подписи, бэкапы и процесс обновления покрыты автоматическими security regression tests.

При этом владелец VPS, участник группы Docker или человек с копией backup технически может извлечь секреты. Полная модель угроз, правила хранения и порядок действий при подозрении на утечку описаны в **[SECURITY.md](./SECURITY.md)**.

## Резервное копирование на VPS

База содержит правила, очередь, аналитику и зашифрованные данные подключения Meta. Файл `.env` содержит ключ, которым эти данные расшифровываются, поэтому полноценная копия должна включать оба компонента. Архивы содержат секреты: не публикуйте их и не прикладывайте к GitHub Issues.

Ручная копия:

```bash
sudo /opt/comment-to-dm/scripts/backup.sh manual
```

Проверка последней копии без изменения рабочей базы:

```bash
sudo /opt/comment-to-dm/scripts/verify-backup.sh
```

Проверка создаёт отдельную временную базу, разворачивает туда архив, проверяет обязательные таблицы и удаляет временную базу. По умолчанию архивы находятся в `/var/backups/comment-to-dm`, доступны только владельцу сервера и удаляются через 14 дней.

Для ежедневного запуска установите systemd units из `deploy/systemd`, включите таймер и сразу создайте первую копию:

```bash
sudo install -m 0644 deploy/systemd/comment-to-dm-backup.service /etc/systemd/system/
sudo install -m 0644 deploy/systemd/comment-to-dm-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now comment-to-dm-backup.timer
sudo systemctl start comment-to-dm-backup.service
```

Копия на том же VPS защищает от неудачного обновления и случайного удаления, но не от потери всего сервера. Периодически скачивайте свежий архив и файл `.sha256` в зашифрованное хранилище или настройте отдельное S3-хранилище.

Полное восстановление изменяет рабочую базу и требует явного подтверждения. Сначала скрипт проверяет архив и создаёт ещё одну страховочную копию:

```bash
sudo COMMENTDM_RESTORE_CONFIRM=RESTORE_COMMENT_TO_DM \
  /opt/comment-to-dm/scripts/restore-backup.sh /var/backups/comment-to-dm/<archive>.tar.gz
```

## Обновление production-сервера

Каждый push в `main` и каждый pull request проверяет отдельный workflow `.github/workflows/ci.yml`: unit-тесты, production build и ESLint. Проверки не меняют работающий сервер.

Для основной установки владельца репозитория push в `main` также запускает `.github/workflows/deploy-hostkey.yml`. После повторных тестов GitHub передаёт архив коммита на VPS. Workflow относится только к серверу сопровождающего проекта; пользовательские self-hosted установки от push не обновляются.

Серверный `scripts/deploy-release.sh` перед каждым обновлением создаёт backup, сохраняет предыдущий Docker-образ, собирает новую версию и ждёт успешного `/ready`. Если база или worker не готовы, скрипт автоматически возвращает предыдущий образ. Production `.env` не передаётся через GitHub и остаётся только на VPS.

Workflow требует четырёх repository secrets:

- `HOSTKEY_HOST` — IP или DNS-имя VPS;
- `HOSTKEY_USER` — отдельный deploy-пользователь;
- `HOSTKEY_SSH_PRIVATE_KEY` — отдельный SSH-ключ только для deploy;
- `HOSTKEY_KNOWN_HOSTS` — заранее проверенный SSH host key сервера.

Эти secrets относятся только к серверу владельца репозитория. Пользовательские self-hosted установки не получают их и не обновляются автоматически без решения владельца.

После объявления проверенного релиза владелец своей установки запускает обновление явно, например:

```bash
sudo /opt/comment-to-dm/scripts/update-vps.sh v0.8.1
```

Скрипт создаёт backup, собирает новую версию отдельно и автоматически откатывает Docker-образ, если `/ready` не подтверждает исправную БД и worker.

## Развёртывание на Railway

Для первой рабочей установки это рекомендуемый вариант. Caddy и `docker-compose.yml` на Railway не используются: платформа сама собирает `Dockerfile`, выдаёт HTTPS-адрес и связывает приложение с PostgreSQL.

1. Создайте новый Railway Project и добавьте PostgreSQL.
2. Добавьте сервис приложения из этого GitHub-репозитория.
3. В сервисе приложения задайте переменные:

```env
NODE_ENV=production
META_MODE=live
PUBLIC_BASE_URL=https://your-service.up.railway.app
ADMIN_PASSWORD=<long-random-password>
SESSION_SECRET=<at-least-43-random-characters>
ENCRYPTION_KEY=<32-random-bytes-in-base64>
META_WEBHOOK_VERIFY_TOKEN=<random-token>
META_GRAPH_VERSION=v25.0
```

4. Добавьте `DATABASE_URL` как reference на переменную PostgreSQL-сервиса.
5. В Public Networking нажмите Generate Domain, затем впишите полученный HTTPS-адрес в `PUBLIC_BASE_URL` и выполните redeploy.
6. Healthcheck `/ready` и restart policy уже определены в `railway.toml`: Railway перезапустит сервис, если БД доступна, но worker перестал обновлять heartbeat.

Одна реплика достаточна. Если Railway временно запустит старую и новую реплики одновременно во время deploy, PostgreSQL leader lease не даст им отправить одно задание параллельно. Постоянное увеличение числа реплик не ускоряет Meta API: у аккаунта остаётся общий лимит.

## Настройка Meta

1. Создайте своё приложение в Meta for Developers и добавьте продукт Instagram API with Instagram Login.
2. Для теста в Development mode добавьте владельца Instagram-аккаунта в роли приложения и примите приглашение.
3. В админке Comment to DM откройте «Подключение». Там показаны точные OAuth callback, webhook URL, скрытый маркер Webhook, URL деавторизации, удаления данных и политики для этой установки.
4. Добавьте OAuth callback в настройки Business Login for Instagram.
5. Добавьте webhook URL в Meta Dashboard, скопируйте маркер Webhook из админки и подпишитесь на поля `comments`, `messages` и `messaging_postbacks`.
6. Укажите Data Deletion и Deauthorize callback URL, показанные в админке.
7. В основных настройках Meta укажите публичную политику конфиденциальности: `https://your-service.up.railway.app/privacy`.
8. Вставьте App ID и App Secret в админке и нажмите «Сохранить и подключить».
9. Авторизуйте профессиональный Instagram-аккаунт на официальной странице Instagram.

Не вводите пароль Instagram в Comment to DM, `.env`, терминал или чужую форму. Пароль должен вводиться только на странице Meta/Instagram.

## Первая проверка

До реального подключения оставьте в `.env`:

```env
NODE_ENV=development
META_MODE=mock
PUBLIC_BASE_URL=http://localhost:3000
```

Создайте правило для слова `гайд` и используйте блок «Тестовый комментарий». После проверки переключите `NODE_ENV=production`, `META_MODE=live`, верните публичный HTTPS URL и пересоберите контейнер.

Для проверки подписки включите переключатель в правиле. Первое сообщение придёт с postback-кнопкой внутри карточки сообщения. Только после нажатия Instagram предоставляет приложению необходимое согласие на чтение статуса подписки. Если подписки ещё нет, пользователь может подписаться и нажать новую кнопку повторно; после подтверждения приложение отправит финальный текст и HTTPS-кнопку.

На реальном аккаунте начните с отдельной тестовой публикации и второго Instagram-аккаунта, который не является автором публикации.

Запустите PostgreSQL и создайте локальный `.env`. Затем:

```bash

```

Интерфейс доступен на `http://localhost:5173`, API — на `http://localhost:3000`.

Полезные проверки:

```bash
npm test
npm run build
npm run lint
```

### Destructive-тесты

`npm run test:integration` очищает таблицы, а `npm run test:migration` выполняет `DROP SCHEMA public CASCADE`.
Оба скрипта запускаются только на отдельной одноразовой базе и отказываются работать, если:

- не задан `INTEGRATION_DATABASE_URL` (fallback на локальную базу удалён);
- не задан `ALLOW_DESTRUCTIVE_TEST_DB=1`;
- имя базы не содержит `test` или `integration`;
- указанная база совпадает с `DATABASE_URL` приложения.

```bash
createdb comment_to_dm_test
ALLOW_DESTRUCTIVE_TEST_DB=1 \
  INTEGRATION_DATABASE_URL=postgres://USER@127.0.0.1:5432/comment_to_dm_test \
  npm run test:migration

createdb comment_to_dm_integration
ALLOW_DESTRUCTIVE_TEST_DB=1 \
  INTEGRATION_DATABASE_URL=postgres://USER@127.0.0.1:5432/comment_to_dm_integration \
  npm run test:integration
```

Integration-тест сам сбрасывает `worker_leases` внутри своей одноразовой базы, поэтому рабочую базу для запуска тестов трогать не нужно. Тест поднимает два worker-процесса и проверяет, что лизу держит ровно один.

Для локальной проверки всплеска запустите приложение с `META_MODE=mock`, задайте пароль в `BURST_ADMIN_PASSWORD` и выполните `npm run test:burst -- http://127.0.0.1:3000 5000 25`. Скрипт принимает 5000 уникальных комментариев с конкуренцией 25, проверяет отсутствие потерь на входе и выводит размер очереди. Он намеренно не запускается в live-режиме.

## Архитектура

- React/Vite — минимальная админка;
- Fastify/TypeScript — OAuth, API и webhooks;
- PostgreSQL — правила, очередь и технический журнал;
- один встроенный worker — последовательная обработка исходящих запросов;
- Caddy — HTTPS и reverse proxy;
- Docker Compose — воспроизводимое развёртывание.

Webhook подтверждается после надёжного сохранения события в базе. Direct имеет повышенный приоритет, но публичные ответы получают каждое пятое окно отправки и не остаются без обработки. При большом backlog включается surge mode: до разгрузки очереди приоритет получают private replies. Worker учитывает `Retry-After`, `X-App-Usage` и `X-Business-Use-Case-Usage`, использует backoff с jitter и автоматически продолжает работу после безопасной паузы. Задания и отложенные follow-up переживают перезапуск контейнера.

### Ограничение Follow to DM

Автоматическое приветствие нового подписчика пока не реализовано. В 2026 году Meta предоставляет это событие только части аккаунтов и партнёров в beta; стандартная webhook-подписка самостоятельного Meta-приложения не содержит события нового подписчика. Приложение не имитирует эту функцию через пароль, cookies или парсинг уведомлений. Когда Meta откроет официальный webhook для текущего типа подключения, триггер можно будет добавить без изменения очереди доставки.

### Что происходит при сбоях

| Сценарий | Реакция приложения |
| --- | --- |
| Meta вернула rate limit | Останавливает весь исходящий поток до `Retry-After` или рассчитанного времени восстановления, затем делает безопасную пробу. |
| Временная ошибка Meta или сети до отправки | Повторяет с экспоненциальной задержкой и jitter. После серии ошибок включает circuit breaker. |
| Соединение оборвалось во время записи | Помечает результат как неопределённый. Публичный ответ сначала сверяет с Instagram; private reply повторяет осторожно и распознаёт ответ «уже отправлено». |
| Токен истёк или отозван | Не расходует очередь, показывает требование переподключения. До истечения long-lived token пытается обновить его автоматически. |
| Пропали разрешения или webhook-подписки | Ставит отправку на паузу, проверяет `comments`, `messages` и `messaging_postbacks` и пытается восстановить их; при необходимости просит действие владельца. |
| Worker или контейнер упал посреди запроса | Watchdog возвращает зависшее задание в состояние сверки, а не считает его безусловно неотправленным. |
| PostgreSQL временно недоступен | Webhook не подтверждается успешным ответом, поэтому Meta может доставить его снова; уникальный `comment_id` предотвращает дубль. Worker продолжит после восстановления БД. |
| Задание старше семи дней | Переводится в `expired`, чтобы не пытаться отправить private reply вне допустимого окна. |

Проверки состояния доступны по `/health` (процесс и БД) и `/ready` (БД и heartbeat активного worker). В панели видны пауза Meta, требование повторной авторизации, проблемы подписки, неопределённые отправки и surge mode.

`QUEUE_INTERVAL_MS` задаёт минимальный стартовый интервал между операциями API, а не гарантированный темп: при росте нагрузки Meta приложение увеличивает его автоматически. `META_REQUEST_TIMEOUT_MS` ограничивает зависший HTTP-запрос, `PROCESSING_TIMEOUT_SECONDS` управляет watchdog, а пороги `SURGE_ENTER_PRIVATE_JOBS` и `SURGE_EXIT_PRIVATE_JOBS` включают и выключают режим всплеска. Не запускайте несколько реплик для ускорения одного Instagram-аккаунта — leader lease намеренно оставит одного отправителя, потому что разрешённая Meta пропускная способность общая.

## Приватность и безопасность

Проект не содержит телеметрии и внешних шрифтов. В рабочем режиме он обращается только к Meta API и URL, открываемым самим пользователем по кнопке. Подробности и модель угроз описаны в [SECURITY.md](./SECURITY.md).

Секреты не должны попадать в Git. Файл `.env` уже исключён через `.gitignore`.

## Ограничения

- Только официальный сценарий private reply после комментария; это не холодная рассылка.
- Первый private reply ограничивается правилами и временным окном Meta.
- Повторный комментарий того же человека под той же публикацией не запускает то же правило второй раз.
- Проверка подписки доступна только после того, как пользователь сам нажал postback-кнопку; обычная URL-кнопка не даёт Meta нужного согласия.
- Live, вложения, сложные цепочки диалогов и несколько Instagram-аккаунтов пока не поддерживаются. Простые входящие Direct и ответы/реакции на Stories уже доступны как отдельные типы правил.
- Версия Graph API настраивается. Перед реальным запуском сверяйте её и разрешения с актуальной документацией Meta.
